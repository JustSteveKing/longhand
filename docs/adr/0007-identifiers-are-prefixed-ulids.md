# ADR 0007: Identifiers are prefixed ULIDs

- **Status:** Accepted
- **Date:** 2026-10-08
- **From:** RFC 0002

## Context

Every resource needs an identifier that is safe to expose, unique across the system, and useful when it turns up somewhere without context: a log, a support ticket, a webhook payload.

## Decision

Resource `id`s are ULIDs with a type prefix (`thr_`, `pst_`, `mem_` and the rest, listed in RFC 0002), generated by the server. Client-generated IDs are not accepted; documents that create several related resources link them with JSON:API's `lid`. Clients treat IDs as opaque strings that may be sorted but not parsed.

## Consequences

- IDs sort by creation time, which gives collections a natural stable tiebreaker.
- An ID says what it identifies wherever it appears.
- The prefix duplicates the JSON:API `type` inside resource objects. That is deliberate, for the many places IDs travel without one.
- Prefixed IDs are longer than bare ULIDs, and the database stores either the prefix or reconstructs it.

## Alternatives

- **UUID v4.** No ordering, and nothing in the value says what it is.
- **Auto-increment integers.** Guessable, and they leak volume.
