# ADR 0047: Embeddings are passages, made in queued jobs and removed in the same transaction as the change that makes them wrong

- **Status:** Accepted
- **Date:** 2026-10-09
- **From:** RFC 0009

## Context

A post can be 40,000 characters, far more than one embedding represents well. Embedding takes a model call, which a write should not wait on. And a vector of text that has since been edited or deleted would let search find content by meaning after it has gone.

## Decision

Searchable text is split into passages of about 2,000 characters on paragraph boundaries, each with its own embedding in one `search_passages` table, recording the model that made it. Embeddings are generated by queued jobs after publishing, editing, resolving or recording. When content is edited, deleted or loses visibility, its passages are removed or updated in the same transaction as that change, before any new embedding exists. Semantic search uses only passages from the current model; changing the model re-embeds everything in the background.

## Consequences

- Writing never waits on a model.
- New content is findable by meaning a few seconds after it is findable by keyword.
- Old text is never found by meaning once it has gone.
- A model change leaves semantic results thin until re-embedding catches up, rather than mixing two vector spaces.

## Alternatives

- **One vector per resource.** Long posts blur into one meaning.
- **Embedding on write.** Every post waits on a provider.
- **Removing stale vectors in the next job.** A window in which deleted text is still findable.
